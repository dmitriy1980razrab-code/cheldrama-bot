# Подключение внешних каналов

Ядро бота не зависит от сайта, VK или MAX. Каждый канал подключается отдельным
адаптером после получения официальных доступов. Секреты хранятся только в переменных
окружения и никогда не добавляются в GitHub.

## Уже развёрнутая инфраструктура

- тестовая ВМ Yandex Cloud с Ubuntu 24.04 и статическим публичным IPv4;
- Nginx перед приложением на закрытом порту `127.0.0.1:8080`;
- тестовый домен `vash-kapeldiner.ru` и бесплатный TLS-сертификат Let's Encrypt;
- автоматическое продление сертификата Certbot, проверенное через `renew --dry-run`;
- постоянно работающая служба бота;
- автоматическое обновление театральных данных четыре раза в сутки;
- ежедневная внешняя резервная копия в закрытом Object Storage;
- проверенное скачивание копии и контрольная сумма SHA-256.

До рабочего подключения каналов остаются официальные секреты и согласование с
администраторами театра. Тестовый HTTPS-адрес можно заменить официальным доменом без
переноса приложения или базы данных.

## Официальный сайт

От администратора сайта потребуется:

- согласованный способ вставки виджета;
- адрес тестовой страницы;
- список разрешённых доменов;
- возможность добавить внешний HTTPS адрес API;
- согласование политики безопасности сайта;
- контакт разработчика для проверки тестовой версии.

## VK

От администратора сообщества потребуется:

- права на подключение сообщений сообщества;
- тестовое сообщество или тестовый режим;
- официальные параметры доступа к API;
- настройка адреса входящих уведомлений;
- секрет подтверждения запросов;
- согласование кнопок, карточек и уведомлений.

## MAX

От администратора официального канала потребуется:

- разрешение на создание и подключение бота;
- официальные параметры доступа;
- настройка адреса входящих событий;
- тестовый контур, если он предоставляется платформой;
- согласование формата карточек и уведомлений.

Рабочая интеграция использует production Webhook по HTTPS. Входящий запрос должен
проверяться по заголовку `X-Max-Bot-Api-Secret`; повторно доставленное событие не
обрабатывается второй раз. Токен передаётся только в заголовке авторизации исходящих
API-запросов. Актуальная документация: https://dev.max.ru/docs-api/methods/POST/subscriptions

## Уже подготовлено без доступов

- единый формат входящего сообщения VK/MAX;
- проверка callback-секрета VK и идентификатора сообщества;
- проверка webhook-секрета MAX;
- разбор текста, ID пользователя, имени и нажатия кнопки;
- журнал идентификаторов входящих событий для защиты от дублей;
- безопасный отказ при повреждённом JSON;
- преобразование ответа ядра в независимую структуру будущего API-запроса.
- серверные маршруты `POST /webhooks/vk` и `POST /webhooks/max`;
- ответ кодом подтверждения при подключении Callback API VK;
- проверка секрета до разбора и обработки пользовательского сообщения;
- безопасное подтверждение принятого события без раскрытия внутренних ошибок;
- ограниченная очередь подготовленных ответов без внешней отправки.

Маршруты не активируются автоматически: до получения официальных секретов и настройки
серверного запуска запросы к ним получают `404`. Подготовленный ответ остаётся во
внутренней ограниченной очереди и не уходит в VK или MAX.

Каждый канал можно включить отдельно. Для VK одновременно требуются callback-секрет,
ID сообщества, код подтверждения и токен отправки; для MAX — Webhook-секрет и токен.
Секреты допускается
загружать из файлов серверного хранилища. Неполный комплект VK считается ошибкой
конфигурации и не позволяет запустить сервер в неопределённом состоянии.

Фактические адреса методов отправки, версии API и параметры кнопок окончательно
фиксируются только после получения тестовых доступов администратора каждого канала.

Подготовлены формирователи исходящих запросов: VK `messages.send` и MAX
`POST https://platform-api2.max.ru/messages`. MAX-токен передаётся только заголовком
`Authorization`, кнопки подписки преобразуются в callback-клавиатуру. Штатный HTTPS-
транспорт активируется только полным комплектом защищённых настроек канала.

Для локальной демонстрации Webhook связан с исходящими адаптерами через ограниченный
фоновый исполнитель. Ошибочная доставка не останавливает обработку следующих ответов.

Постоянная очередь реализована в защищённой базе подписчиков. Штатный Webhook сохраняет
в ней зашифрованный ответ до подтверждения события платформе. Повтор события блокируется
HMAC-ключом, а незавершённая доставка восстанавливается после истечения аренды. Перед
рабочий запуск связывает её с HTTPS-транспортом и управляемым циклом доставки.

Управляемый серверный цикл подготовлен и проверен на тестовом транспорте. Он просыпается
при добавлении ответа, ограничивает размер выборки, безопасно останавливается и выдаёт
только агрегированное состояние очереди. Реальный транспорт запускается после загрузки
официальных токенов из защищённых файлов.

Сервисные напоминания и уведомления об изменении спектаклей подключены к общей
зашифрованной очереди. Состояние `sent` исходного уведомления устанавливается только
после успешной доставки. Непосредственно перед отправкой повторно проверяются активная
подписка и последнее согласие; отписка отменяет уже подготовленное сообщение.

Подтверждённые рекламные кампании также подключены к общей очереди. Получатели
формируются только после наступления запланированного времени с учётом канала и
предпочтений. Перед каждой отправкой повторно проверяется рекламное согласие.

## Перед рабочим запуском

- проверить актуальную официальную документацию каждой платформы;
- использовать отдельные тестовые и рабочие секреты;
- заменить тестовый домен официальным после согласования с театром;
- ограничить разрешённые источники запросов;
- проверить восстановление базы подписчиков и защитить архив целиком до появления
  реальных персональных данных;
- утвердить тексты согласий и правила обработки персональных данных;
- провести нагрузочную и функциональную проверку.
